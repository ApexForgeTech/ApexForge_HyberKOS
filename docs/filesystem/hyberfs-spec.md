# HyberFS user-space snapshot format, version 2

This document specifies the Phase 15/16 prototype implemented by `hyber-fs`.
Integers are unsigned and little-endian; no compiler struct layout is stored.
Version 1 images are rejected without writes. There is no in-place migration:
export them with the old reader and import into a new version 2 image. Never
use `format --force` as a migration command; it destroys the previous volume.

## Geometry and lifetime

Blocks are exactly 4096 bytes. A device contains 8 through 32769 whole blocks.
The upper bound limits snapshot decoding/allocation to 64 MiB per slot and
must change only with a reviewed streaming/extent implementation.

For `B` blocks, let `S = floor((B - 1) / 2) * 4096` bytes. Block 0 is the
superblock. Slot 0 starts at byte 4096; slot 1 starts at `4096 + S`. Each slot
has `S` bytes. An optional final unused block is reserved. Each slot contains
a 40-byte header and at most `S - 40` bytes of payload. Regions never overlap.

The root object is ID 1. IDs increase monotonically, are never recycled, and
remain valid until namespace deletion. The low-level snapshot API has no open
handle table: read/write calls resolve paths for each operation; unlink removes
an object immediately. Open-handle retention belongs to the future HyberFS VFS
provider. `Volume` is a trusted storage API, not an authorization boundary.

## Superblock (4096 bytes)

| Offset | Width | Meaning |
|---|---:|---|
| 0 | 8 | Magic bytes `HYBFS15\0` |
| 8 | 4 | Version, exactly 2 |
| 12 | 8 | Device block count, exactly matching device length |
| 20 | 12 | Reserved, all zero |
| 32 | 8 | FNV-1a-64 over bytes `[0,32)` followed by `[40,56)` |
| 40 | 16 | Random volume identifier, opaque bytes |
| 56 | 4040 | Reserved, all zero |

The identifier is generated by the hosted OS entropy provider at format time.
It is not an access credential. The superblock is immutable after formatting;
normal commits cannot tear geometry metadata. Root ID, block size, and region
locations are fixed/derived by this version. No optional feature bits are defined.

## Slot header (40 bytes)

| Offset | Width | Meaning |
|---|---:|---|
| 0 | 8 | Magic bytes `HYBFS15\0` |
| 8 | 4 | Version, exactly 2 |
| 12 | 8 | Nonzero generation |
| 20 | 8 | Payload byte length, at most slot capacity |
| 28 | 8 | FNV-1a-64 over header `[0,28)` followed by payload |
| 36 | 4 | Reserved, all zero |

The FNV offset basis is `0xcbf29ce484222325`; for each byte, XOR then multiply
by `0x100000001b3` modulo 2^64. This detects accidental damage; it is not a MAC.
It covers generation, length, format, metadata, and file data.
An all-zero header means an unused/invalidated slot.

## Payload

Every scalar occupies eight bytes except `kind` (one byte). Strings and byte
arrays have an eight-byte length then that many bytes, with no padding.
Owner, group, mode, and flags occupy eight bytes but must fit in u32.
Counts/sizes must fit the bounded payload; truncated fields are rejected.

State starts with `next_object_id`, `root_object_id`, `object_count`.
Object records follow in increasing ID order:

```text
id
kind                       1=file, 2=directory
owner, group, mode
created, modified          Unix seconds; zero is unspecified
flags                      zero; unknown flags rejected
extended_metadata_count    at most 64
  key_length, UTF-8 key    1..128 bytes, no NUL
  value_length, value      0..4096 opaque bytes
data_length, file_data
entry_count
  name_length, UTF-8 name  1..255 bytes; no NUL, slash, . or ..
  child_object_id
```

Metadata keys and directory names are encoded sorted. Duplicate keys, names,
IDs, or trailing payload bytes are invalid. Modes permit only rwx bits
(`0..0777`). Modified time cannot precede creation time. Creation and content
writes use hosted Unix seconds; same-second writes may share a timestamp.

Every non-root object has exactly one parent; hard links are unsupported.
Root must be a directory. Files have no entries; directories have no file
bytes. All objects must be reachable. Cycles, multiple parents, dangling
references, and next-ID regressions fail validation. Graph traversal is
iterative, avoiding recursion on deeply nested input.

## Commit, crash recovery, and errors

1. Validate state and capacity.
2. Zero the inactive slot header and flush.
3. Write the complete inactive payload and flush.
4. Write its generation/checksum header and flush.
5. Publish the new generation in memory. Never rewrite the superblock.

Mount validates both slots independently, including their object graphs.
It selects the highest valid generation. Equal generations with different
states are corruption. Device I/O errors abort mount. Corrupt slots are
exposed through `Volume::recovery_warnings()`; `hyberfsck` exits nonzero on
damage even if the other slot is readable. Authentication loading refuses
damaged-slot recovery to avoid silently restoring an old credential snapshot.
Recovered volumes with damaged slots are read-only; export readable data to
a fresh volume rather than overwriting potentially recoverable evidence.
No in-place orphan repair discards user objects.

A failed commit may have persisted the old or new complete transaction.
The volume becomes unwritable until remount. Successful sync/unmount requires
all flushes to succeed. Unsynced mutations are not durable. `into_device`
deliberately does not sync (crash tests); `unmount` does sync.

Capacity/name/mode failures leave the previous in-memory state intact.
Growth is checked before allocation, including sparse writes and truncate.
Holes are zero-filled; append writes at EOF; empty writes do not extend files.
Rename does not replace an existing target. Renaming an existing path to
itself succeeds. Moving a directory inside itself fails.
`replace_file` stages complete file data and metadata with rollback; sync
commits it together with any other pending mutations.

Format invalidates both old slot headers before generation 1. Formatting is
destructive and is not crash-atomic. CLI format requires `--force`; auth
provisioning creates a new image exclusively. Existing-image open never
creates or resizes files. FileDevice checks bounds and uses advisory
shared/exclusive image locks. New hosted images use mode 0600 on Unix.

## Verification and boundaries

`hyberfsck <image>` opens read-only and exits nonzero on damage or I/O failure.
`hyberfs-tool check <image> <blocks>` validates the selected snapshot and prints
recovery diagnostics. Tests cover interrupted writes/flushes, partial headers,
generation corruption, graph validation, reformat, capacity rollback, huge
offsets, and 400 deterministic reference-model operations with remount.
These simulate BlockDevice durability, not physical hardware power cuts.

This version uses a snapshot journal and slot capacity accounting. Native
extents, per-block allocation bitmaps, record-log replay, kernel handles,
encryption, and kernel VFS integration need later storage work and a format
migration. Invalid snapshots are reported, not silently repaired.
